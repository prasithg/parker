# Plan: "Hey Parker" — local wake word for the companion

Date: 2026-09-01

Status: chairman-directed (Pras: "a robot with just power on and looking
lifeless until I say hey parker, at which point eyes and antenna pop up
and listen intently — as much visual as audial"); implements R2 of
[`2026-09-01-always-available-reachy-companion.md`](2026-09-01-always-available-reachy-companion.md).

## Engine decision

**Chosen: local keyword spotting on the already-shipped faster-whisper.**
While dormant, the companion streams mic PCM (16 kHz) to the local engine
over `ws /parker/converse/wake` — localhost only, nothing leaves the
machine. The engine keeps a ~2.4 s rolling window, runs the warmed
transcriber every ~0.7 s of new audio **only when the window has real
energy** (silence never spins the CPU), and matches "hey + parker-like"
with a fuzzy grammar tuned for effortful/variable speech.

Alternatives rejected:

- **Picovoice Porcupine**: best-in-class latency, but a commercial
  license/account key inside a public MIT project — wrong posture.
- **openWakeWord in-browser (onnxruntime-web)**: no pretrained
  "hey parker" model (custom training is its own project), plus multi-MB
  vendored WASM in the patient surface. A future upgrade path once a
  custom model is trained on consented samples.
- **Web Speech API**: Chrome implementations ship audio to Google — that
  violates "no cloud audio while dormant" outright.

Trade-offs accepted for v1: wake latency ~1–2 s (window + hop + ASR),
continuous low CPU while someone is speaking near the mic (energy gate
keeps quiet rooms free). Both journaled/measurable; the brief's
wake-recall/false-wake metrics come from receipts.

## Semantics

```text
power off      -> nothing runs, nothing listens (unchanged)
power on       -> DORMANT: mic held locally, wake ws open, cloud CLOSED,
                  Reachy lifeless (head sunk, ember eyes barely lit)
"hey parker"   -> wake ws fires -> visual POP (head springs up, eyes snap
                  open bright, antennae perk with overshoot) + soft chirp
                  -> realtime line opens (greeting = the audible ack)
active session -> full duplex as shipped (spoken confirmation etc.)
long quiet     -> the bridge's gentle wrap-up -> goodbye -> closing ->
                  browser drains audio, closes the line, returns to
                  DORMANT (wake listening re-arms; power stays on)
power off      -> everything released, persisted off
```

- Mic ownership is explicit: ONE getUserMedia per power-on, an owner
  object routes frames by mode (`wake` → local ws @16 kHz, `live` →
  realtime ws @24 kHz). Wake→active reuses the held stream — no
  re-prompt, fast activation. Output/mic AudioContexts are created on
  the power gesture and live for the powered-on lifetime (a wake event
  is not a user gesture and could not create them).
- The companion-mode ladder skip is REMOVED: with dormancy to return to,
  the wrap-up → goodbye → closing ladder is exactly the brief's
  "one gentle optional wrap-up"; his voice still stands it down.
- Ambient speech while dormant animates nothing: the expression machine
  gains a `dormant` phase (non-active, overlays cleared, energy ignored)
  and a `wake_detected` event that only fires from dormant.
- If the local model is unavailable, power-on falls back to
  straight-active (take-2 behavior) with an honest card — never a
  silently broken switch.
- Wake evidence: each detection logs a receipt (matched text, window
  energy, latency) and the expression receipts carry
  `dormant -> connecting (wake_detected)` for session review.

## Matcher (PD-speech tolerant, false-wake averse)

Normalized transcript must contain a greeting token ("hey/hay/hi/a/eh")
within two tokens before a parker-like token (exact set + edit-distance
≤1 from "parker"). Bare "parker" without a greeting does NOT wake
(mentioning Parker on TV must not). Unit-tested matrix includes
negatives ("hey partner", "parking", "hey park the car") and effortful
positives ("hey... parker", "hey parka").
